## 1. 项目摘要

本项目使用两块硬件相同、职责不同的 STM32F103C8T6 最小系统板，完成 MPU6050 六轴惯性数据采集、上电校准、零漂抑制、Mahony 姿态融合、四元数与欧拉角输出、双板高速通信、CRC16 校验、指定序号重传、PC 实时曲线显示以及 Mahony 参数在线闭环调节。

最终数据链路为：

```text
MPU6050
  │ I2C1，400 kHz，地址 0x68
  ▼
STM32F103C8 从机
  │ TIM2 产生 1 ms 节拍
  │ 1 kHz 读取、校准、Mahony 解算
  │ Quaternion + Roll/Pitch/Yaw
  │ 36 Byte 自定义帧 + SEQ + CRC16
  ▼ USART1，921600 bps，8N1
STM32F103C8 主机
  │ 帧同步、CRC 检查、错误统计、请求重传
  │ 100 Hz 输出 Roll/Pitch/Yaw
  ▼ USART2，115200 bps，8N1
CH340 USB-TTL
  ▼
Python 上位机 / VOFA+
```

反向控制链路为：

```text
Python 输入 Kp/Ki
  │ ASCII：KP=x,KI=y\n
  ▼
主机解析并构造 SET_GAINS（CMD 0x03，16 Byte，CRC16）
  ▼
从机校验并调用 Mahony_SetGains()
  ▼
从机返回 GAIN_ACK（CMD 0x04，36 Byte，CRC16，同一 SEQ）
  ▼
主机校验 ACK，向 PC 输出 GAIN_OK,kp,ki\n
  ▼
Python 状态从 Sent 更新为 Confirmed
```

最终验证结果包括：从机采样率稳定为 `1000 Hz`、`imu_overrun_count = 0`；主机正常接收约 `999~1000 frame/s`；常态 CRC/协议错误为 0；故障注入后完成 `SEQ=3000` 的 CRC 检出与指定帧重传；在线参数成功修改为 `Kp=1.5、Ki≈0.01`；Python 界面实测出现 `Confirmed: Kp=2.000000, Ki=0.030000`，同时 `Valid frames=6717、Parse errors=0`。

## 2. 考核任务拆解与完成情况

依据考核题截图和完整开发对话，任务可拆为四部分。

| 考核部分 | 具体要求 | 最终状态 | 主要证据 |
|---|---|---:|---|
| 从机姿态解算 | 定时器节拍触发 MPU6050 采样，稳定 1 kHz | 完成 | `imu_sample_rate=1000`，`imu_overrun_count=0` |
| 从机姿态解算 | 上电自校准、零漂抑制 | 完成 | 1000 点陀螺仪零偏平均 + `±0.15 °/s` 死区 |
| 从机姿态解算 | 输出 Pitch、Roll、Yaw、Quaternion | 完成 | `mahony.q0~q3`、`roll/pitch/yaw` 持续随动作更新 |
| 双板通信 | 每 1 ms 发送一帧姿态数据 | 完成 | 36 Byte 帧，USART1 921600，约 1000 帧/s |
| 双板通信 | 自定义协议、SEQ、CRC 校验 | 完成 | `AA 55` 帧头、CMD/LEN/SEQ/Payload/CRC16 |
| 双板通信 | CRC 失败请求重传 | 完成 | 故障注入 `SEQ=3000`，`retransmit_success_count=1` |
| 上位机 | 实时显示三轴角度和波形 | 完成 | VOFA+ 三通道；Python Tkinter + matplotlib 三曲线 |
| 上位机 | 动态修改滤波加权系数 | 完成 | `SET_GAINS 0x03` → `Mahony_SetGains()` |
| 上位机 | 对参数写入做闭环确认 | 超额完成 | `GAIN_ACK 0x04`、`GAIN_OK`、GUI `Confirmed` |
| 提交材料 | 接线图 | 已给出完整绘图规范 | 建议使用嘉立创 EDA 绘制模块级原理图 |
| 提交材料 | 开发文档 | 完成 | 本文档 |

一个重要的实现说明：题目所说的“定时器触发 I2C 读取”，本项目采用工程上更安全的方式实现——TIM2 中断只置位 `imu_sample_flag`，主循环检测标志后执行 I2C 读取。它仍由 1 ms 定时节拍驱动采样，但避免在中断服务函数内进行阻塞式 I2C 和浮点姿态计算。

## 3. 系统角色与总体设计

### 3.1 为什么使用两块相同的 STM32

两块板的芯片相同，但软件角色不同：

| 节点 | 职责 | 关键外设 |
|---|---|---|
| 从机 STM32 | MPU6050 采样、数据换算、校准、Mahony 解算、姿态打包、历史帧缓存、响应重传、应用在线参数、返回 ACK | I2C1、TIM2、USART1 |
| 主机 STM32 | 板间帧同步、协议解析、CRC 校验、错误重传请求、PC 数据输出、PC 命令解析、参数转发、ACK 匹配 | USART1、USART2 |
| PC 上位机 | 选择串口、显示角度、绘制曲线、统计有效帧/解析错误、输入 Kp/Ki、显示参数确认状态 | CH340 虚拟串口 |

这种拆分隔离了“高频实时采样/算法”和“通信/人机交互”。即使 PC 绘图或串口文本输出发生短时抖动，从机仍能保持 1 kHz 姿态任务。

### 3.2 主要数据频率

| 链路/任务 | 频率 | 数据形式 |
|---|---:|---|
| TIM2 采样节拍 | 1000 Hz | 每 1 ms 置一次采样标志 |
| MPU6050 读取 | 1000 Hz | 从 `0x3B` 连续读取 14 Byte |
| Mahony 更新 | 1000 Hz | `dt=0.001f` |
| 从机 → 主机姿态帧 | 1000 帧/s | 36 Byte 二进制协议帧 |
| 主机 → PC 姿态输出 | 100 Hz | `roll,pitch,yaw\n` ASCII |
| PC → 主机调参 | 按需 | `KP=...,KI=...\n` |
| 主机 ↔ 从机重传/调参/ACK | 按事件 | CMD `0x02/0x03/0x04` |

36 Byte 姿态帧在 1000 帧/s 时有效载荷流量约 36 kB/s。按 UART 每字节约 10 bit 计算，线路占用约 360 kbps，低于 921600 bps，留有足够余量。

## 4. 硬件与接线

### 4.1 MPU6050 与从机

| MPU6050 | 从机 STM32F103C8 | 说明 |
|---|---|---|
| VCC | 3.3V | 传感器供电 |
| GND | GND | 共地 |
| SCL | PB6 / I2C1_SCL | I2C 时钟 |
| SDA | PB7 / I2C1_SDA | I2C 数据 |
| AD0 | GND | 7 位地址固定为 `0x68` |
| XDA | 不接 | 本项目不用辅助 I2C |
| XCL | 不接 | 本项目不用辅助 I2C |
| INT | 不接 | 本项目使用 TIM2 周期采样，不使用数据就绪中断 |

HAL 的设备地址参数使用左移后的地址：

```c
#define MPU6050_ADDR (0x68 << 1)
```

### 4.2 从机与主机

| 从机 | 主机 | 方向 |
|---|---|---|
| PA9 / USART1_TX | PA10 / USART1_RX | 从机 → 主机 |
| PA10 / USART1_RX | PA9 / USART1_TX | 主机 → 从机 |
| GND | GND | 必须共地 |

USART 必须 TX 交叉接 RX。两块板分别由 USB 供电时，只连接信号线和 GND，不要再互连 3.3V/5V 电源轨。

### 4.3 主机与 USB-TTL

| 主机 | USB-TTL | 方向 |
|---|---|---|
| PA2 / USART2_TX | RXD | 主机 → PC |
| PA3 / USART2_RX | TXD | PC → 主机 |
| GND | GND | 共地 |

主机已有独立供电时不连接 USB-TTL 的 5V。TTL 电平优先使用 3.3V。

### 4.4 ST-Link

| ST-Link | STM32 |
|---|---|
| SWDIO | PA13 / SWDIO |
| SWCLK | PA14 / SWCLK |
| GND | GND |

板子已由 USB 供电时，ST-Link 的 3.3V 不必接。项目只有一个 ST-Link 也不影响双板调试：烧录后的 MCU 可脱离 ST-Link 独立运行，因此一块板正常供电运行，另一块板连接 ST-Link 查看 Watch 即可。

### 4.5 接线图绘制建议

最终提交建议使用嘉立创 EDA 新建“原理图”，画模块级连接图，不必展开两块最小系统板内部的全部晶振、BOOT、电源去耦与 48 个封装引脚。

```text
             MPU6050
                │ I2C1 / 400 kHz
                ▼
       STM32F103C8 Slave
                ⇅ USART1 / 921600 / 8N1
       STM32F103C8 Master
                ⇅ USART2 / 115200 / 8N1
             USB-TTL
                │ USB
                ▼
               PC
```

图纸右下角建议附注：

```text
1. Slave and Master must share GND.
2. USART TX connects to RX.
3. MPU6050 is connected only to Slave I2C1.
4. USB-TTL is connected only to Master USART2.
5. Two STM32 boards are powered independently; do not connect 5V/3.3V rails together.
```

## 7. 从零开发全过程

### 7.1 先定角色和开发顺序

项目没有直接把两块 STM32、MPU6050、USB-TTL 和全部协议一次性接上，而是采用分层验证：

```text
最小 I2C / WHO_AM_I
→ 正式 MPU6050 驱动
→ 数据换算
→ 校准与零漂抑制
→ 1 kHz 定时采样
→ Mahony 姿态解算
→ 双板单字节 UART
→ 正式协议和 CRC
→ 故障注入与重传
→ 主机-PC 与 VOFA+
→ SET_GAINS
→ Python 上位机
→ GAIN_ACK 闭环
```

该顺序的核心经验是：每次只引入一个新的不确定因素，先拿到可观察的 Watch 证据，再继续扩展。

### 7.2 最小 I2C 与 WHO_AM_I 排查

第一次工程只配置 I2C1，不加入 TIM、UART、Mahony 和模块化驱动。目标只有：

```text
HAL_I2C_IsDeviceReady()
HAL_I2C_Mem_Read(WHO_AM_I, 0x75)
期望 who_am_i == 0x68
```

早期出现过一个调试假象：全局变量默认为 0，而 `HAL_OK` 也等于 0，因此程序还未执行到 I2C 代码时，Watch 仍可能显示 `HAL_OK`。为避免误判，测试变量先初始化为明显的哨兵值，例如 `who_am_i=0xFF`、状态为 `HAL_ERROR`，并在 `while(1)` 处断点确认代码确实执行完。

第一块标称 MPU6050 的模块实测：

```text
i2c_ready       = HAL_OK
i2c_read_status = HAL_OK
who_am_i        = 0x70
```

这说明供电、PB6/PB7、地址 `0x68`、I2C 时序和 HAL 读寄存器均已工作，但 `0x70` 不符合标准 MPU6050 的 `WHO_AM_I=0x68`，更接近 MPU6500 或兼容器件。为了与题目和驱动寄存器行为保持一致，最终更换模块。

新模块实测：

```text
who_am_i        = 0x68
i2c_ready       = HAL_OK
i2c_read_status = HAL_OK
pwr_mgmt_1      = 0x40
pwr_read_status = HAL_OK
```

`PWR_MGMT_1=0x40` 说明上电默认 `SLEEP=1`，与 MPU6050 预期一致。由此确认替换后的模块用于后续开发。

另一次完整工程上电后曾出现：

```text
imu_init_status  = HAL_BUSY
imu_calib_status = HAL_ERROR
imu_sample_rate  = 0
```

此时故障发生在最底层 I2C 初始化阶段，并非协议或 Mahony。重新插拔、检查 PB6/PB7/供电并完整断电上电后恢复为 `HAL_OK`。经验是：再次遇到 `HAL_BUSY` 时，优先排查接触、总线占用和上电状态，不要先改高层代码。

### 7.3 MPU6050 驱动模块化

确认身份寄存器后，才建立 `mpu6050.h/.c`，避免在最初 bring-up 阶段同时引入新文件、Include Path 和 Keil Group 问题。

最终初始化流程：

| 步骤 | 寄存器 | 写入值 | 含义 |
|---:|---|---:|---|
| 1 | `WHO_AM_I 0x75` | 读取 `0x68` | 身份检查 |
| 2 | `PWR_MGMT_1 0x6B` | `0x80` | 器件复位 |
| 3 | `PWR_MGMT_1 0x6B` | `0x01` | 唤醒，使用 X 轴陀螺仪 PLL |
| 4 | `CONFIG 0x1A` | `0x03` | DLPF_CFG=3 |
| 5 | `SMPLRT_DIV 0x19` | `0x00` | 1 kHz / (1+0) = 1 kHz |
| 6 | `GYRO_CONFIG 0x1B` | `0x18` | FS_SEL=3，±2000 °/s |
| 7 | `ACCEL_CONFIG 0x1C` | `0x10` | AFS_SEL=2，±8 g |

每次从 `ACCEL_XOUT_H (0x3B)` 连续读取 14 Byte，按大端寄存器顺序组合：`AX、AY、AZ、TEMP、GX、GY、GZ`。

### 7.4 原始数据与物理量换算

最终换算关系：

```text
ax_g = raw_ax / 4096.0
ay_g = raw_ay / 4096.0
az_g = raw_az / 4096.0

gx_dps = raw_gx / 16.4
gy_dps = raw_gy / 16.4
gz_dps = raw_gz / 16.4

temperature_C = raw_temp / 340.0 + 36.53
```

代表性静止 Watch 快照之一：

| 数据 | 原始值 | 换算值 |
|---|---:|---:|
| AX | -6 | -0.0029296875 g |
| AY | -80 | -0.01953125 g |
| AZ | 4363 | 1.06396484 g |
| GX | 29 | 1.76829267 °/s |
| GY | -12 | -0.73170733 °/s |
| GZ | 0 | 0 °/s |
| TEMP | -3914 | 25.0182343 °C |

另一静止快照为 `ax=-37、ay=-82、az=4352、gx=29、gy=-11、gz=0`。按量程换算后，Z 轴约为 1.063 g，符合模块平放、Z 轴朝上的预期；未校准的陀螺仪仍有约 `+1.77 °/s` 和 `-0.67~-0.73 °/s` 的静态零偏。

### 7.5 上电校准与零漂抑制

最终使用：

```c
MPU6050_CalibrateGyro(&gyro_bias, 1000);
```

校准过程为：

1. 清零旧 bias；
2. 等待 200 ms，让传感器稳定；
3. 模块保持完全静止；
4. 连续读取 1000 组原始陀螺仪数据，每组间隔 1 ms；
5. 使用 `int64_t sum_gx/sum_gy/sum_gz` 累加；
6. 求平均并除以 `16.4`，得到 `gyro_bias.gx/gy/gz`，单位 °/s；
7. 每次正式测量后执行 `MPU6050_ApplyGyroBias()`；
8. 对校准后的三轴角速度应用 `MPU6050_GYRO_DEADBAND=0.15f`，即绝对值小于 0.15 °/s 时置 0。

因此本项目的零漂抑制由三层共同完成：上电静态零偏平均、残余角速度死区、Mahony 积分反馈。

### 7.6 TIM2 1 kHz 采样框架

中断回调只做轻量级调度：

```text
TIM2 Update
  ├─ imu_sample_flag == 0：置 1，imu_timer_tick_count++
  └─ imu_sample_flag != 0：imu_overrun_count++
```

主循环检测 `imu_sample_flag` 后依次执行：

```text
MPU6050_ReadRaw()
→ MPU6050_ConvertRaw()
→ MPU6050_ApplyGyroBias()
→ Mahony_UpdateIMU(..., 0.001f)
→ imu_sample_count++
→ 构造并发送姿态帧
```

每秒使用 `imu_sample_count - rate_last_sample_count` 计算 `imu_sample_rate`。代表性 Watch：

```text
imu_timer_tick_count = 0x0000BF55
imu_sample_count     = 0x0000BF55
imu_sample_rate      = 0x000003E8 = 1000
imu_overrun_count    = 0
```

这证明 TIM2 的每次节拍基本都对应一次成功采样，没有漏采和主循环处理超时。

### 7.7 Mahony 六轴姿态解算

`Mahony_t` 保存：

```text
q0, q1, q2, q3
integral_x, integral_y, integral_z
kp, ki
roll, pitch, yaw
```

上电默认初始化：

```c
Mahony_Init(&mahony, 2.0f, 0.02f);
```

每 1 ms 调用：

```c
Mahony_UpdateIMU(
    &mahony,
    imu_data.gx, imu_data.gy, imu_data.gz,
    imu_data.ax, imu_data.ay, imu_data.az,
    0.001f
);
```

核心处理包括：角速度从 °/s 转 rad/s、加速度归一化、用当前四元数估计重力方向、叉乘得到姿态误差、Kp 比例反馈、Ki 积分反馈、四元数积分、四元数归一化以及 `atan2f/asinf` 转欧拉角。Pitch 计算前对 `asin` 输入限制到 `[-1,1]`，避免浮点误差导致数值越界。

代表性静止结果：

```text
mahony.roll  ≈ -1.28°
mahony.pitch ≈  0.98°
mahony.yaw   ≈ -28.61°

q0 ≈  0.969
q1 ≈ -0.009
q2 ≈  0.011
q3 ≈ -0.247
```

四元数模长约为 1，Roll/Pitch 接近水平面。MPU6050 没有磁力计，因此 Yaw 没有绝对航向参考，会随初值和陀螺仪积分产生缓慢漂移；这不是实现错误，而是六轴 IMU 的物理限制。

### 7.8 双板 USART 最小验证

正式协议前先验证 921600 bps 的物理链路。

第一步：从机每秒发送 `0x55`，主机使用 USART1 中断逐字节接收。主机代表性 Watch：

```text
uart_rx_start_status = HAL_OK
uart_rx_byte         = 0x55
uart_rx_count        = 0x2E = 46
uart_rx_55_count     = 0x2E = 46
```

46 个接收字节全部是 `0x55`，证明从机 TX、主机 RX、交叉接线、共地、921600 配置和中断重复接收均正确。

第二步：主机收到 `0x55` 后回复 `0xAA`，从机中断接收。代表性清洁快照中主机接收/回复计数均为 8，从机曾观察到 `uart_rx_byte=0xAA、uart_rx_count=0x15、uart_rx_aa_count=0x15`。由此确认 USART1 双向全双工链路通过。

这一步暴露过一个重要代码位置错误：主机回复 `0xAA` 的代码被误放进 `Error_Handler()`，正常运行永远不会执行，导致 `uart_reply_pending=1`，但 `uart_reply_status` 保持初始 `HAL_ERROR`、`uart_tx_aa_count=0`。将发送代码移回 `main()` 的 `while(1)` 后恢复。

### 7.9 36 Byte 正式姿态协议

基础 UART 通过后，停止 `0x55/0xAA` 测试字节，避免污染正式流。主从机共用 `crc16` 和 `protocol` 模块。

#### 7.9.1 通用约定

```text
多字节整数：Little Endian
浮点数：IEEE-754 float32，Little Endian
CRC：CRC-16/CCITT-FALSE
Polynomial：0x1021
Initial Value：0xFFFF
帧头：0xAA 0x55
```

#### 7.9.2 ATTITUDE，CMD 0x01

| Byte | 长度 | 字段 | 说明 |
|---:|---:|---|---|
| 0 | 1 | HEADER1 | `0xAA` |
| 1 | 1 | HEADER2 | `0x55` |
| 2 | 1 | CMD | `0x01` |
| 3 | 1 | LEN | `28` |
| 4~5 | 2 | SEQ | `uint16_t`，小端 |
| 6~9 | 4 | q0 | float32 |
| 10~13 | 4 | q1 | float32 |
| 14~17 | 4 | q2 | float32 |
| 18~21 | 4 | q3 | float32 |
| 22~25 | 4 | roll | float32，degree |
| 26~29 | 4 | pitch | float32，degree |
| 30~33 | 4 | yaw | float32，degree |
| 34~35 | 2 | CRC16 | 小端 |

CRC 覆盖 `frame[2]` 到 `frame[33]`，共 32 Byte，即 `CMD + LEN + SEQ + Payload`，不包含 `AA 55` 帧头。

从机每次 Mahony 更新后构造帧并使用 USART1 发送。主机接收状态机按：等待 `0xAA` → 等待 `0x55` → 一次中断接收剩余 34 Byte → 主循环按 CMD 解析。正常代表性结果：

```text
从机：
imu_init_status         = HAL_OK
imu_read_status         = HAL_OK
imu_calib_status        = HAL_OK
imu_sample_rate         = 1000
imu_overrun_count       = 0
attitude_tx_status      = HAL_OK
attitude_tx_count       = 0x4066（持续增长）
attitude_tx_error_count = 0
attitude_tx_sequence    = 0x4067

主机：
uart_rx_start_status    = HAL_OK
protocol_last_status    = PROTOCOL_OK
frame_rate              = 0x3E8 = 1000
frame_crc_error_count   = 0
frame_other_error_count = 0
received_sequence       = 持续变化
```

### 7.10 CRC 故障注入、SEQ 和错误重传

#### 7.10.1 历史帧缓存

从机维护：

```c
#define ATTITUDE_HISTORY_SIZE 16
```

缓存最近 16 个正确的 36 Byte 姿态帧和对应序号，共占用约 `16 × 36 = 576 Byte` 的帧数据存储，另有序号和有效标志。环形写指针覆盖最旧帧。

#### 7.10.2 RETRANSMIT，CMD 0x02

| Byte | 长度 | 字段 | 值/说明 |
|---:|---:|---|---|
| 0~1 | 2 | Header | `AA 55` |
| 2 | 1 | CMD | `0x02` |
| 3 | 1 | LEN | `0` |
| 4~5 | 2 | Requested SEQ | 小端 |
| 6~7 | 2 | CRC16 | 对 Byte 2~5 共 4 Byte 计算 |

主机姿态帧解析器在 CRC 比较前先提取 SEQ。因此即使 CRC 失败，仍知道需要请求哪一个序号。CRC 错误时：

```text
frame_crc_error_count++
retransmit_request_sequence = received_sequence
retransmit_request_pending = 1
```

主机重新挂起 UART 接收后，再阻塞发送 8 Byte 重传请求，设置 `retransmit_waiting` 和 `retransmit_waiting_sequence`。从机解析请求，在 16 帧历史缓存中查找并重发原始正确帧；主机收到相同 SEQ 且 CRC 正确后，`retransmit_success_count++` 并清除等待标志。

#### 7.10.3 可控故障注入

从机定义：

```c
#define PROTOCOL_TEST_CORRUPT_SEQUENCE 3000
volatile uint8_t protocol_test_enable = 0;
```

测试时临时置 `protocol_test_enable=1`。当 `attitude_tx_sequence==3000` 时，先把正确帧保存到历史缓存，再执行：

```c
attitude_tx_frame[10] ^= 0x01;
```

但不重新计算 CRC，主机必然检出错误，而历史缓存中仍保留可重传的正确版本。

最终闭环实测：

```text
frame_crc_error_count             = 1
retransmit_request_tx_status      = HAL_OK
retransmit_request_tx_count       = 1
retransmit_request_tx_error_count = 0
retransmit_waiting_sequence       = 0x0BB8 = 3000
retransmit_waiting                = 0
retransmit_success_count          = 1
frame_other_error_count           = 0
frame_rate                        ≈ 999~1000
```

中途曾截到 `retransmit_waiting=1、retransmit_success_count=0`，这只是请求已发出但正确帧尚未返回的瞬时状态；稍后变为等待清零、成功计数 1，闭环才算完成。验证后必须把 `protocol_test_enable` 恢复为 0；当前最终源码已确认是 0。

### 7.11 主机到 PC 与 VOFA+ 联调

先使用最小文本：

```text

```

主机每秒通过 USART2 非阻塞发送。VOFA+ 使用 `RawData` 引擎可直接看到文本。若使用 `FireWater`，文本不会按预期显示，因为 FireWater 用于解析逗号分隔的数值通道。

实测：

```text
pc_test_tx_count        = 0x51 = 81
```

随后改为每 10 ms 输出：

```c

```

即 100 Hz 的 `Roll,Pitch,Yaw`。使用 `HAL_UART_Transmit_IT()`，并用 `pc_attitude_tx_busy` 防止上一包未完成时重入；USART2 发送完成回调清零 busy。VOFA+ 切换到 FireWater 后显示 I0/I1/I2 三条曲线，样例：

```text

```

Watch 曾显示：

### 7.12 PC 命令解析与 SET_GAINS 在线调参

#### 7.12.1 PC 到主机的 ASCII 接口

PC 发送格式：

```text

```

主机 USART2 中断逐字节接收：忽略 `\r`，遇 `\n` 时追加 `\0` 并置 `pc_command_pending=1`，主循环通过：

```c
sscanf(pc_rx_line, "KP=%f,KI=%f", &new_kp, &new_ki)
```

解析。

曾出现完整字符串已收到但数值不更新：

```text
pc_rx_start_status      = HAL_OK
pc_rx_line              = "KP=3.00,KI=0.05"
pc_kp                   = 0
pc_ki                   = 0
pc_gain_cmd_count       = 0
pc_gain_cmd_error_count = 0
```

因为成功和错误计数都没变化，可确定不是 `sscanf` 格式失败，而是解析块根本没有执行。检查发现代码在 `while(1)` 外。移入循环后：

```text
pc_kp                   = 3
pc_ki                   = 0.0500000007
pc_gain_cmd_count       = 1
pc_gain_cmd_error_count = 0
pc_command_pending      = 0
```

`0.0500000007` 是 float 的正常二进制表示误差。

#### 7.12.2 SET_GAINS，CMD 0x03

| Byte | 长度 | 字段 | 说明 |
|---:|---:|---|---|
| 0~1 | 2 | Header | `AA 55` |
| 2 | 1 | CMD | `0x03` |
| 3 | 1 | LEN | `8` |
| 4~5 | 2 | SEQ | 小端 |
| 6~9 | 4 | Kp | float32，小端 |
| 10~13 | 4 | Ki | float32，小端 |
| 14~15 | 2 | CRC16 | 对 Byte 2~13 共 12 Byte 计算 |

主机代表性发送结果：

```text
pc_kp                 = 3
pc_ki                 = 0.0500000007
pc_gain_cmd_count     = 1
gains_tx_status       = HAL_OK
gains_tx_count        = 1
gains_tx_error_count  = 0
gains_tx_sequence     = 1
```

第一包实际使用 SEQ 0，发送成功后自增为 1。

从机原接收器只能固定收 8 Byte 重传请求，因此升级为可变命令状态机：

```text
等 AA
→ 等 55
→ 接收 CMD + LEN
→ CMD=0x02 且 LEN=0：继续收至 8 Byte
→ CMD=0x03 且 LEN=8：继续收至 16 Byte
→ 主循环按 CMD 分派
```

收到并通过 CRC 后执行：

```c
Mahony_SetGains(&mahony, set_gains_kp, set_gains_ki);
```

不能调用 `Mahony_Init()`，因为 Init 会重置四元数、积分项和欧拉角；`Mahony_SetGains()` 只修改 `filter->kp` 和 `filter->ki`，姿态状态连续。

在线调参实测：

```text
mahony.kp              = 1.5
mahony.ki              = 0.00999999978 ≈ 0.01
set_gains_status       = PROTOCOL_OK
set_gains_sequence     = 1
set_gains_kp           = 1.5
set_gains_ki           ≈ 0.01
set_gains_count        = 2
set_gains_error_count  = 0
imu_sample_rate        = 1000
imu_overrun_count      = 0
```

说明参数从 PC 经主机真正进入从机滤波器，且没有破坏 1 kHz 姿态任务。

这些参数保存在 RAM：运行时无需重新编译和烧录，但 Reset/掉电后会回到默认 `Kp=2.0、Ki=0.02`。题目未要求掉电保存，因此没有引入 Flash 参数存储。

### 7.13 SET_GAINS 后的 CRC 重传回归

从机状态机同时支持 `0x02` 8 Byte 和 `0x03` 16 Byte 后，重新打开一次 `protocol_test_enable` 做回归。最终再次得到：

### 7.15 GAIN_ACK 闭环确认

仅显示 `Sent` 只能证明 Python 把字符串写入串口，不能独立证明从机已通过 CRC 并应用参数。因此增加闭环 ACK。

#### 7.15.1 GAIN_ACK，CMD 0x04

为了复用主机固定 36 Byte 的从机接收状态机，ACK 也设计为 36 Byte：

| Byte | 长度 | 字段 | 说明 |
|---:|---:|---|---|
| 0~1 | 2 | Header | `AA 55` |
| 2 | 1 | CMD | `0x04` |
| 3 | 1 | LEN | `28` |
| 4~5 | 2 | SEQ | 与 SET_GAINS 相同 |
| 6~9 | 4 | Applied Kp | 从机当前 `mahony.kp` |
| 10~13 | 4 | Applied Ki | 从机当前 `mahony.ki` |
| 14 | 1 | Result | `0x00 = OK` |
| 15~33 | 19 | Reserved | 构帧前 `memset` 为 0 |
| 34~35 | 2 | CRC16 | 对 Byte 2~33 共 32 Byte 计算 |

ACK 返回的是实际应用后的 `mahony.kp/mahony.ki`，不是把收到的载荷原样回显。

从机调参成功后置 `gains_ack_pending=1`。下一个 1 ms 发送槽用 ACK 替代普通 ATTITUDE 帧，再下一毫秒恢复姿态帧。这样不会突然额外占用一包 UART 带宽；代价是该秒 `frame_rate` 可能短暂显示 999，但 `imu_sample_rate` 应继续为 1000，`imu_overrun_count=0`。

主机发送 SET_GAINS 时记录：

```text
gains_waiting = 1
gains_waiting_sequence = 本次发送的 SEQ
```

收到 36 Byte 后先看 CMD：`0x01` 解析姿态，`0x04` 解析 ACK。只有 CRC 正确、Result=OK、正在等待且 ACK SEQ 与等待 SEQ 相同，才执行：

```text
gains_ack_count++
gains_waiting = 0
pc_gain_ack_pending = 1
```

随后 USART2 优先向 Python 发送：

```text
GAIN_OK,2.000000,0.030000\n
```

Python 后台线程先识别 `GAIN_OK,`，将消息放入队列；GUI 线程收到 `gain_ack` 后把状态更新为：

```text
Confirmed: Kp=2.000000, Ki=0.030000
```

最终截图确认：

```text
Status: Confirmed: Kp=2.000000, Ki=0.030000
Valid frames: 6717
Parse errors: 0
```

这证明完整闭环为：Python → 主机 → SET_GAINS+CRC → 从机 → `Mahony_SetGains()` → GAIN_ACK+CRC → 主机 → `GAIN_OK` → Python `Confirmed`，且 ACK 扩展没有破坏正常姿态文本解析。

## 12. 最终验收步骤

### 12.1 上电前

1. 检查 MPU6050 5 根线；确认 AD0 接 GND。
2. 检查两块 STM32 的 USART1 TX/RX 交叉和 GND 共地。
3. 检查主机 PA2/PA3 与 USB-TTL RX/TX 交叉。

### 12.2 从机底层验收

1. 上电校准期间保持 MPU6050 静止约 1.2 s 以上（200 ms 稳定等待 + 1000×1 ms 采样，另有初始化耗时）。

## 13. 设计限制与边界

1. **Yaw 漂移**：没有磁力计，Yaw 只能靠陀螺仪积分，无法获得绝对航向。Roll/Pitch 可借助重力方向长期校正。
2. **参数掉电不保存**：Kp/Ki 在线写入 RAM，复位后回默认 `2.0/0.02`。若需要持久化，可增加 Flash 参数页、版本号和 CRC。
3. **重传窗口有限**：历史缓存只有 16 帧，在 1000 Hz 下只覆盖最近约 16 ms。当前点对点高速 UART 通常足够；复杂链路可扩大缓存或降低数据率。
4. **SEQ 为 uint16**：1000 帧/s 时约 65.536 s 回绕一次。当前相等比较和短时重传不受影响，但长期乱序统计应按模 65536 处理。
5. **阻塞发送**：从机姿态帧和若干控制帧使用阻塞式 HAL UART。当前 921600 bps 下 36 Byte 约 0.39 ms，实测仍能保持 1 kHz；若继续扩展负载，建议改 DMA/双缓冲。
6. **校准要求静止**：上电时若移动模块，所得陀螺仪 bias 会污染后续角速度。可在未来加入静止检测和校准失败提示。
7. **加速度未做六面校准**：当前只做物理量比例换算，`az≈1.064 g` 的比例/零偏误差尚未通过六面标定修正；Mahony 会归一化加速度向量，因此不妨碍本次考核。

## 14. 工程经验总结

1. **最小系统优先**：第一次只验证 WHO_AM_I，不提前引入姿态算法和第二块板。
2. **用证据分层定位**：`i2c_ready`、`pc_rx_line`、计数器和状态枚举能快速判断故障在哪一层。
3. **成功计数和错误计数都为 0 往往意味着代码没执行**，而不是输入既成功又失败。
4. **编译报错位置不一定是根因位置**：函数开头报错常由前面少括号/分号造成。
5. **磁盘文件不等于工程文件**：Keil 的链接错误优先检查 `.c` 是否加入 Group。
6. **中断只做必要工作**：TIM2 中断只置标志，I2C、浮点算法和协议在主循环完成。
7. **每加一种协议命令都要做回归**：加入 SET_GAINS 后重新验证 RETRANSMIT；加入 ACK 后继续观察姿态解析错误。
8. **ACK 应确认实际状态，不应只回显输入**：本项目返回 `mahony.kp/ki`，并匹配 SEQ。
9. **测试钩子必须有正式开关**：故障注入通过 `protocol_test_enable` 控制，发布版明确为 0。
10. **文本链路与二进制链路分层**：板间使用紧凑二进制协议，PC 侧使用易调试 ASCII，实现简单且职责清晰。
11. **一个 ST-Link 足够**：烧录后让一块板独立运行，另一块连接调试器观察，交替验证两端。
12. **保存阶段性截图**：WHO_AM_I、1 kHz、CRC 重传、在线调参和 GUI Confirmed 都应作为答辩证据链。

## 15. 答辩建议与常见问答

### 15.1 推荐演示顺序

1. 展示模块级接线图，说明三条总线和主从角色。
2. 展示从机 Watch：`imu_sample_rate=1000、overrun=0`。
3. 轻转 MPU6050，展示 Python 的 R/P/Y 数值和三条曲线。
4. 说明主机每秒约收 1000 个 36 Byte 姿态帧，PC 只显示 100 Hz。
5. 展示故障注入截图：`SEQ=3000、CRC error=1、retransmit success=1`。
6. 在 GUI 修改 Kp/Ki，重点展示 `Sent → Confirmed`。
7. 最后指出正常运行 `Parse errors=0`，并说明 Yaw 漂移边界。

### 15.2 可能问题及回答要点

**为什么两块相同 STM32 不合并？**  
考核要求双板通信；同时从机隔离 1 kHz 实时采样/解算，主机负责协议、重传和 PC 交互，职责清楚、调试可分层。

**为什么 USART1 用 921600？**  
姿态帧 36 Byte × 1000 帧/s 约 36 kB/s，考虑起止位约 360 kbps。921600 有足够余量，实测 frame_rate 为 999~1000 且错误为 0。

**为什么主机到 PC 只发 100 Hz？**  
人眼曲线显示不需要 1 kHz；降为 100 Hz 可减少 ASCII 格式化、USB-TTL 和 GUI 绘图负担，不影响从机 1 kHz 算法。

**CRC 覆盖哪些字段？为什么不覆盖帧头？**  
覆盖 CMD、LEN、SEQ 和 Payload；帧头用于同步，不参与本协议 CRC。主从实现完全一致。

**如何证明重传真的成功？**  
从机在 SEQ 3000 的发送副本中翻转一个 bit、保留历史正确帧；主机 CRC 错误计数 +1，发出请求 3000，从机按历史缓存重发，主机收到相同 SEQ 且 CRC 正确后成功计数 +1。

**Kp/Ki 是 PID 吗？**  
Mahony 中是比例和积分反馈，更接近 PI 结构，不是完整经典 PID 控制器。

**在线调参是否需要每次重新烧录？**  
不需要。固件只需一次烧入“接收并应用参数”的规则；之后参数通过串口写入 RAM。复位后恢复默认值。

**为什么 ACK 设计为 36 Byte？**  
复用主机已验证的固定 36 Byte 接收状态机，仅按 CMD 区分 ATTITUDE 与 GAIN_ACK，降低改动和回归风险。

**如何证明参数不是只到主机？**  
从机只有在 CRC 正确并执行 `Mahony_SetGains()` 后，才把实际 `mahony.kp/ki` 构造成 ACK；Python 收到匹配 ACK 后才显示 Confirmed。

**为什么 Yaw 会漂？**  
MPU6050 只有加速度计和陀螺仪，没有磁场绝对参考。重力只能修正 Roll/Pitch，不能约束绕重力轴的 Yaw。

**为何不在 TIM2 中断里直接读 I2C？**  
阻塞式 I2C 和浮点解算放在 ISR 会拉长中断时间。中断置标志、主循环执行任务，更容易统计 overrun 并保持系统可扩展。

## 16. 可继续优化的方向

1. 使用 USART1 DMA + 双缓冲发送姿态帧，进一步降低 CPU 阻塞。
2. I2C 使用 DMA 或数据就绪 INT，引入超时恢复和总线复位。
3. 增加 Flash 参数持久化、版本号、范围检查和参数 CRC。
4. 为 SET_GAINS 增加 Kp/Ki 合法范围与 NaN/Inf 检查，并定义失败 ACK result。
5. 增加 ACK 超时、参数命令重试和上位机 ACK 计数/超时提示。
6. 扩大历史帧缓存或增加丢帧统计，处理 SEQ 回绕。
7. 加入三轴加速度六面校准和温度补偿。
8. 若需绝对航向，改用带磁力计的九轴 IMU 并扩展 Mahony/Madgwick MARG 更新。
9. 上位机增加数据记录、CSV 导出、参数预设和一键测试报告。
10. 为协议编写主机端单元测试，覆盖 CRC、大小端、非法长度和损坏帧。

## 17. 最终结论

本项目按照“底层硬件 → 驱动 → 实时采样 → 姿态算法 → 单字节链路 → 正式协议 → 错误恢复 → PC 联调 → 在线调参 → ACK 闭环”的顺序完成。
